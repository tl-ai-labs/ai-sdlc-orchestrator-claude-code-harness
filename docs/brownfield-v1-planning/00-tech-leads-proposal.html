Brownfield Mode — Proposal for Tech Leads

Proposal · Brownfield mode for the AI-SDLC Orchestrator plugin · v1 scope

Executive summary

Extend the SDLC plugin from empty-folder demos to real, existing repositories — safely, across many sessions, with hard guarantees.

The AI-SDLC Orchestrator today only works in an empty folder. Every install doc says "open Claude Code in an empty folder." That gates its usefulness at pilot / demo. This proposal takes it to production repos: any stack, unknown pre-existing configuration, real teammates, real CI — without touching anything the operator hasn't approved. Read on for cost impact, the routing mechanism, real usage walkthroughs, the safety story, scope decisions, and the ask.

The problem — and the shape of the solution

Where we are

Greenfield-only

Plugin runs a 9-phase pipeline that assumes an empty folder — reads a brief, writes fresh code to ./src, hard-codes NestJS+Prisma task types, never inspects the target repo. Every real user has a real repo with real conventions, real AI tools already in place, real CI, real teammates. Today's plugin is a demo — not a product they can use.

Where we're going

Brownfield-capable

New command installs onto any existing repo. Does one of seven kinds of work — docs, bugfix, feature-extend, feature-new, refactor, test, deps — with a non-destructive write contract that guarantees off-limits files (theirs and ours) are never touched. Multi-session machinery makes the second and Nth session on the same project safe and coherent.

How the routing works — the core mechanism

The 10× cost reduction isn't magic. It's a policy-driven phase-based routing: judgment work stays on the premium model where quality matters; mechanical pattern-matching work goes to a cheap fast model. Every dispatch is logged with its actual model + token count + cost.

Which kind of work → which tier

Kind of work Tier Model in default policy
Judgment — discovery, requirements, architecture / change plan, packet planning, senior code review, security review premium Claude Opus
Mechanical — codegen packets, doc packets, test-code packets, debug packets mechanical Gemini Flash
Escalation — after 2 mechanical retries fail premium Claude Opus (auto)
Test execution — running the actual test command local Bash on machine — no model call

Per intent — which phases fire, at which tier

Only which phases fire changes per intent — tier assignment stays stable.

Intent Judgment phases (premium) Mechanical phases (Flash)
docs requirements, senior review, security review doc_addition, doc_update
bugfix requirements (reproduce + diagnose), senior review, security review bug_reproduce, bug_diagnose, bug_fix_apply, test_add
feature-extend requirements, architecture (change plan), senior review, security review edit + add mix
feature-new requirements, architecture (full subsystem), senior review, security review full codegen mix
refactor requirements (delta), architecture (refactor plan), senior review, security review refactor_extract, patch_apply
test requirements (coverage target), senior review, security review test_backfill, test_add
deps requirements (upgrade list), architecture (dep-swap plan), senior review, security review dependency_add, adjacent-code patches
Advanced (v1.5). The policy YAML supports per-task-type overrides. Example: route bug_diagnose to premium even though it's inside the mechanical codegen phase, because diagnosis is really judgment. Not shipping in v1 — phase-level defaults are enough. Users on custom policies can add these rules themselves.

Configurable — teams can override

Team wants everything on Anthropic (no Gemini)Ship opus-only policy; higher cost per run but single-vendor
Team needs on-prem / private-cloud endpointsDrop a routing-policy.yaml at repo root pointing at Bedrock / Vertex / self-hosted (v1.5 ships example policies)
Team wants a specific task-type on premium tierPer-task-type overrides in policy YAML (v1.5 — v1 uses phase-level defaults)
Cost cap per runHard cap in policy (default $50); run aborts cleanly when hit

How it works — two prompts, six shepherded sections

The user runs two prompts, ever. Setup completes in the first; task work runs in the second. Every step is shepherded — the plugin auto-does what it can, pauses and guides the user when human action is required, verifies each fix before continuing.

Prompt 1 · setup — six sections

Everything ready in one guided pass

  1. Install — marketplace, plugin, MCP dist
  2. Environment — Node, git, permissions, conflicts
  3. Repo detection — branches the flow
  4. Credentials — discover first, ask second (scans shell env, gcloud, home dir configs, repo files, code references)
  5. Repo setup — Tier 1 discovery, adaptive profile if triggered, baseline save, pipeline pre-check (6 smoke steps)
  6. Summary — status report + next-step guidance
Prompt 2 · task — lean and cached

Fast, focused on the actual work

  1. Setup-status check — resumes shepherd if setup was interrupted
  2. Staleness check — cached baseline or 5-10s incremental refresh
  3. Intent brief — short interview drafts the task description
  4. Gate 0 — one confirmation screen: intent + scope
  5. Pipeline runs — phase-by-phase, gates at requirements, design, security, and final acceptance

Sample task walkthroughs — what real usage looks like

Three sessions on the same repo. Different intents, different developers, no clobbering. Each session sees the prior work via the committed .sdlc/ ledger.

Monday Session 1 · first use

Developer runs /sdlc-brownfield

  1. Plugin scans repo. Detects Node/TypeScript + Nest. Notices .cursor/rules and custom .mcp.json — marks them off-limits.
  2. Gate 0 asks intent. User picks docs — needs a README for the auth module.
  3. Pipeline runs. Writes docs/auth.md; edits main README to link it.
  4. Report. 1 new file, 1 edited, $0.14. Nothing outside src/auth/** and docs/ touched. Ledger row appended.
Tuesday Session 2 · same user

Same developer runs /sdlc-brownfield

  1. Setup-status: complete. Baseline is 3 commits old — incremental refresh (~5 s).
  2. Gate 0. User picks bugfix — the /login endpoint returns 500 when password field is missing.
  3. Pipeline runs. Reproduces the bug → diagnoses → applies fix → adds regression test.
  4. Report. 2 files edited, 1 test added, $0.32. Cursor rules, .mcp.json, and Monday's docs untouched.
Friday Session 3 · different developer

Second developer runs /sdlc-brownfield

  1. Sees Monday + Tuesday runs in .sdlc/ledger.md (committed, pulled with the branch).
  2. Incremental refresh only re-hashes the 8 files that changed since Tuesday.
  3. Fresh Gate 0. Their own choice of intent — nothing carries over from other devs' runs.
Why the second developer sees prior work automatically. Plugin owns .sdlc/CLAUDE-SDLC.md; the user's CLAUDE.md gets a single @.sdlc/CLAUDE-SDLC.md import line at setup (with a diff preview). Every future session — with or without the plugin installed — loads the plugin-owned context via that import. We never modify user-authored text beyond that one line.

The safety story — three enforcement layers

The plugin is a guest in a house that already has residents. It never touches files outside a confirmed allowlist. Three layers protect against that promise being broken — the third is unbreakable at the tool boundary.

1

The written contract — orchestrator prompt

The AI reads its instructions and mostly obeys the allowlist. Soft; can drift.

Soft
2

The project manager — packet validator

Every planned file-write is checked against the allowlist before dispatch.

Schema
3

The locked door — PreToolUse hook

Every single file-write is refused at the tool boundary if outside the allowlist. On by default in brownfield mode. Escape hatch --strict-write=off.

Hard

What's in v1 · what's next · what's later

The scope has been deliberately shaped. We ship what makes the second, third, and Nth session on the same real project safe and coherent — deferring quality-of-life features until the base is proven with real users.

Backward compatibility guarantee: the existing /sdlc-run command (greenfield mode for empty folders) continues to work unchanged. This is an extension, not a replacement. Regression tests exercise the existing greenfield example. Nothing that works today breaks.

The seven intents

docs

Documentation

API docs, README, ADRs, runbooks, JSDoc, architecture diagrams.

bugfix

Bug fixes

Reproduce → diagnose → fix → regression test, one pass.

feature-extend

Extend a feature

Add a field, param, filter, or flag to something that exists.

feature-new

New feature

A new endpoint, screen, or module in an existing app.

refactor

Refactor

Rename, extract, consolidate — safety-first across many files.

test

Backfill tests

Coverage push, missing tests, flaky-test fixes.

deps

Deps & security

Dependency upgrades, CVE patches, deprecated-API replacements.

Note: PR / code review is deferred to v2 — it's a different product category from safely-changing-code (competes with CodeQL, Cursor review, GitHub Copilot review) and not core to v1's value prop.

Risks & how we handle them

Every known setup-time and runtime risk gets detection + clear message + inline choice — never elaborate solving infrastructure when a good detection suffices. Sample:

User already runs Cursor / Aider / Copilot on the same repoDetected at discovery; default off-limits for their config; surfaced at confirmation gate
Custom in-house framework unknown to usAdaptive stack profile samples the repo and learns conventions from real files
Missing Gemini credential mid-setupShepherd guides setup or offers to switch to opus-only policy (10× cost, one-off tradeoff)
Repo has failing tests before we startDetected at pre-check; user confirms whether to proceed without test phase
A run goes badPer-file provenance records SHA before/after; single-run rollback via a revert command
Session dies mid-setupSetup progress persisted per section; next task command resumes shepherd from where it left off
Cost runaway on unexpectedly large repoHard per-run cost cap in policy; run aborts cleanly when hit
